# Задание: надёжный вход в ThreadsGo через подтверждение в Telegram

Подготовлено 16.09.2026 по локальному коду, исходный commit `06cad9c`.

**Статус:** реализовано локально 16.09.2026. Добавлены challenge-обмен, подтверждение кнопкой в боте, восстановление и polling исходной вкладки, исправление подписи `last_name`, миграция и тесты. Production-выкладка не выполнялась в соответствии с ограничением в разделе 12.

## 1. Решение и ожидаемый результат

Да, сценарий реализуем на существующих FastAPI + aiogram + SQLAlchemy + React. Добавить подтверждение входа в чате бота как дополнительный способ на странице `/login`. Сохранить рабочий вход через Telegram-виджет. В новом сценарии Mini App не открывать.

Путь пользователя:

1. На сайте принять существующие обязательные условия и нажать «Войти через бота Telegram».
2. Сайт создаёт запрос входа и открывает конкретного бота со специальной ссылкой. Исходная вкладка остаётся на экране ожидания.
3. При необходимости пользователь нажимает Start в Telegram. Бот показывает: «Подтвердить вход в ThreadsGo?» и кнопки «Да, войти» / «Отменить».
4. После «Да, войти» бот пишет: «Готово! Теперь вернитесь во вкладку сайта, где вы начали вход. Авторизация завершится автоматически».
5. Исходная вкладка получает результат, сохраняет обычный JWT проекта и открывает кабинет; без подписки — страницу тарифов.

На телефоне браузер может приостановить фоновую вкладку: тогда завершение произойдёт сразу после возвращения в неё. Нельзя гарантировать автоматическое переключение из Telegram в исходный браузер. Обычная ссылка «Открыть сайт» может открыть другой браузер или встроенный браузер Telegram; не обещать, что такая новая вкладка уже авторизована. Гарантия относится к вкладке, начавшей вход и сохранившей секрет запроса.

Использовать два существующих/простых механизма: aiogram получает нажатие кнопки через уже работающий long polling Telegram; сайт раз в несколько секунд опрашивает наш API. WebSocket, SSE, Redis и новый публичный webhook в первой версии не нужны. Запросы входа хранить в существующей БД, не в словаре процесса.

## 2. Что найдено в текущем коде

| Место | Текущее поведение / проблема | Действие |
| --- | --- | --- |

| `frontend/src/api/client.ts`: `TelegramAuthPayload` | В типе тоже отсутствует `last_name`; функция отправляет spread исходного объекта. | Добавить опциональную фамилию, не удалять её до проверки. |

| `app/telegram/bot.py`: `start_handler` | Аргументы `/start` не разбираются. Всегда выдаётся `WebAppInfo(/login)` либо обычная ссылка `/login`. | Обрабатывать `login_<secret>` до обычного приветствия. |
| `LoginPage.tsx`, `client.ts` | JWT записывается в localStorage того окружения, в котором открыт сайт. Mini App не передаёт его исходному браузеру. | Выдавать JWT исходной вкладке через защищённый обмен. |
| `LoginPage.tsx`: `loadTelegramWebAppScript` | Ожидание заканчивается через 1200/1600 мс; при поздней загрузке `initData` не перечитывается этим же запуском. | Если сохраняется Mini App, исправить отдельный путь загрузки и повторной попытки. |
| `LoginPage.tsx`: виджет | Наличие iframe трактуется как готовность. Это не доказывает, что пользователь может завершить вход. | Альтернативная кнопка должна быть доступна независимо от результата загрузки виджета. |
| `app/api/auth.py`: `_sync_subscription_after_login` | Перед выдачей JWT ожидается проверка подписки через Telegram; в `subscriptions.py` несколько запросов выполняются последовательно, общего короткого таймаута нет. | Ограничить общее ожидание, не превращать недоступность проверки подписки в отказ входа. |
| `client.ts`: ошибки входа | Есть сообщение посетителю «backend запущен на 127.0.0.1:8000»; разные причины отказа смешиваются. | Заменить понятными сообщениями и кодами причин. |
| `auth.ts`, `ProtectedRoute.tsx` | Наличие токена считается достаточным; срок и действительность проверяются уже последующими API-запросами. | Сохранить совместимость, исправить поведение при недействительном токене и сохранение пути возврата. |
| `app/api/auth.py`: `/login`; `app/api/deps.py` | Пароль выдаёт общий административный токен; tenant API требует Telegram JWT. На текущей странице нет пользовательской формы пароля. | Не предлагать общий административный пароль как способ входа клиентов. |

Ошибка фамилии воспроизведена локально на синтетических данных и тестовом ключе: без `last_name` — accepted; с `last_name` — `401 Invalid Telegram auth hash`. Существующие пять тестов `tests.test_subscription_login_sync` проходят, но фамилию не проверяют.

Не проверялись реальные неудачные входы клиентов, серверные логи, актуальные настройки BotFather и production окружение. Поэтому ошибка фамилии подтверждена кодом и воспроизведением, но не объявляется единственной причиной жалоб. Проблемы домена, сети, allowlist, несовпадения ботов и нескольких polling-процессов требуют отдельной проверки при выкладке.

## 3. Исправление существующего входа — обязательная часть

1. Добавить `last_name: str | None = None` в серверный `TelegramAuthPayload` и `last_name?: string` в TypeScript.
2. При проверке подписи включать все фактически переданные поддерживаемые Telegram-поля, кроме `hash`; локальную `attribution` по-прежнему исключать. Не обрезать строки, не менять регистр/Unicode и не подставлять значения до проверки. Отсутствующее поле и переданная пустая строка — разные случаи.
3. Сохранять фамилию в `User` для устранения этой ошибки не требуется.
4. Некорректные/чрезмерные `auth_date`, неверный JSON и неверный тип Telegram ID должны давать управляемый 4xx, а не 500. Проверку возраста и подписи не ослаблять. Отдельно проверить корректные подписанные Mini App данные по их собственному алгоритму.
5. Добавить регрессионные тесты: фамилия есть/отсутствует/пуста, Unicode, нет username/photo, подмена поля, неверная подпись, истёкшая дата, attribution не участвует в подписи. В тестах брать текущее время или фиксировать часы, не использовать дату, которая со временем окажется неподходящей.

## 4. Модель запроса входа

Добавить модель `TelegramLoginChallenge` и новую Alembic-миграцию после актуального head. Рекомендуемые поля:

| Поле | Назначение |
| --- | --- |
| `id` | Публичный случайный идентификатор, например `secrets.token_urlsafe(16)`, PK. Сам по себе не даёт права входа. |
| `browser_secret_hash` | SHA-256 отдельного `secrets.token_urlsafe(32)`; исходный секрет получает только вкладка сайта. |
| `bot_secret_hash` | SHA-256 другого независимого `secrets.token_urlsafe(32)`; уникальный индекс для поиска по `/start`. |
| `status` | `pending`, `approved`, `denied`, `cancelled`, `consumed`; истечение вычисляется по серверным часам. |
| `created_at`, `expires_at` | UTC, срок попытки 5 минут; индекс по `expires_at`. |
| `telegram_id` | Nullable; заполняется атомарно при первом валидном `/start login_…` в личном чате. |
| `telegram_profile_json` | Только нужные поля профиля из доверенного Telegram update. Не принимать их от браузера. |
| `approved_at`, `consumed_at` | Аудит состояния. |
| `user_id` | Nullable FK на `users.id`, заполняется при завершении входа. |
| `attribution_json` | Проверенная существующей схемой attribution, полученная от исходной вкладки. |
| `display_code` | Короткий код для визуального сопоставления запроса в браузере и боте; не является паролем. |
| `result_token_encrypted`, `result_retry_until` | Короткий зашифрованный кеш результата завершения для безопасного повтора после потери HTTP-ответа. |

На старте возвращать исходные секреты только по HTTPS в ответе инициирующей вкладке. В БД — хеши секретов; в Telegram — только bot secret. Browser secret запрещено помещать в Telegram-ссылку, URL страницы, логи, аналитику или referrer. JWT не передавать через ссылку или сообщение бота.

Сравнение секретов — constant-time. Ограничить длины входов и размер attribution. Для SQLite определить единообразное представление UTC и протестировать сравнения timezone-aware/naive дат.

Переходы: `pending → approved → consumed`; `pending → denied`; `pending/approved → cancelled`. Истёкшие незавершённые запросы не одобряются и не завершаются. Повтор callback для того же пользователя должен быть идемпотентным. Состояния обновлять условным SQL UPDATE с проверкой текущего состояния и количества изменённых строк. Один процессный lock и один `SELECT FOR UPDATE` не решают гонки на SQLite.

Очистка: периодически удалять закончившиеся запросы и профиль/attribution, например спустя час; кеш JWT очищать сразу после `result_retry_until`. Очистку встроить в существующий scheduler либо выполнять ограниченными пакетами при создании/завершении запросов. Проверка срока обязательна независимо от успешности очистки.

## 5. Контракт API

Все маршруты под `/api/v1/auth/telegram-bot`. Не требуют уже существующего пользовательского JWT. Для status/complete/cancel обязательны `challenge_id` и `browser_secret` в JSON-теле POST; не передавать секрет query-параметром. Auth-ответы: `Cache-Control: no-store`.

| Метод и путь | Запрос | Результат |
| --- | --- | --- |
| `POST /start` | `{ attribution? }` | `201`: `{ challenge_id, browser_secret, bot_url, expires_at, poll_interval_ms: 3000, display_code }` |
| `POST /status` | `{ challenge_id, browser_secret }` | `200`: `{ status, expires_at }`, без JWT и без профиля пользователя. `status` включает `pending/approved/denied/cancelled/expired/consumed`. |
| `POST /complete` | `{ challenge_id, browser_secret }` | После одобрения: существующий `LoginResponse` с `access_token`, `token_type`. |
| `POST /cancel` | `{ challenge_id, browser_secret }` | Идемпотентная отмена принадлежащей вкладке незавершённой попытки. Уже выданный JWT эта операция не отзывает. |

Единые машиночитаемые ошибки: `challenge_invalid`, `challenge_pending`, `challenge_expired`, `challenge_denied`, `challenge_cancelled`, `challenge_consumed`, `access_denied`, `bot_unavailable`. Для отсутствующей попытки и неверного секрета одинаковый ответ без раскрытия состояния. Различимые terminal-ошибки возвращать только после успешной проверки browser secret. Временную недоступность БД/бота не выдавать за отказ пользователя.

`/complete` выполняет:

1. Проверить browser secret, срок, `approved`, текущий allowlist и наличие подтверждённого Telegram ID.
2. Найти/создать того же `User` по уникальному `telegram_id`. При параллельной регистрации корректно обработать unique conflict, затем перечитать пользователя. Не заводить новый аккаунт, не переносить/терять проекты и подписку.
3. Перенести attribution с исходного браузера с существующей семантикой first-touch. Данные бота могут не содержать фото: не обнулять имеющееся `photo_url` просто из-за отсутствия его в Bot API update. Username, если удалён пользователем, можно актуализировать.
4. Сохранить существующую синхронизацию подписки, но ограничить общее ожидание, например 3 сек. Сетевые вызовы не выполнять под долгой блокировкой/транзакцией записи challenge. При отмене по таймауту выполнить rollback/refresh нужной DB-сессии; не продолжать с повреждённой транзакцией. Отказ проверки подписки не запрещает авторизацию и не выдаёт платный доступ.
5. Повторно атомарно проверить срок/состояние (за время работы могла прийти отмена), выпустить обычный JWT проекта, сохранить зашифрованный результат и отметить `consumed` одной транзакцией. Нельзя вернуть JWT до успешного commit.
6. Повторный `/complete` с тем же browser secret в течение 60 секунд после `consumed_at` возвращает **тот же** результат, а не новый JWT. Это окно действует и если исходные 5 минут закончились уже после успешного consume. Повторно проверить allowlist. После окна — `challenge_consumed`, новая попытка обязательна.

Для кеша результата можно использовать существующие `encrypt_secret`/`decrypt_secret` из `app/core/secrets.py`; при включении функции проверить корректность `DATA_ENCRYPTION_KEY`, не сохранять JWT открытым текстом. Под конкурентными `/complete` только один результат становится сохранённым; проигравший читает его после commit победителя. Невозможно обеспечить надёжную доставку HTTP-ответа простым необратимым consume без идемпотентного повтора.

Выделить общий сервис работы с Telegram-профилем/сессиями, чтобы бот не импортировал API router и не подделывал `TelegramAuthPayload(hash='…')`. Проверка widget/Mini App подписи остаётся в соответствующем входе; данные Bot API доверяются только обработчику настоящего update. Не делать публичный `/approve`, принимающий Telegram ID со слов браузера.

Лимиты: создание примерно 10/мин на IP; status примерно 30/мин на challenge плюс более широкий IP-лимит, рассчитанный на пользователей за общим NAT; complete/cancel отдельные небольшие лимиты. При 3-секундном polling получается 20 status/мин: текущие 10/мин переносить сюда нельзя. Уважать `Retry-After`. Доверять forwarded IP только от настроенного reverse proxy, не любому заголовку клиента.

## 6. Изменения бота

1. Разобрать аргументы `/start` через aiogram `CommandObject` либо подходящий фильтр. `login_` + 43 символа bot secret укладывается в лимит Telegram start-параметра 64 символа.
2. Только личный чат, `message.from_user` существует и не бот. Найти запрос по хешу секрета, проверить TTL/состояние. Атомарно связать ещё не занятый запрос с этим `from_user.id`. Повтор того же пользователя разрешён; другой Telegram ID не может переопределить связь.
3. Показать домен из доверенного `PUBLIC_APP_URL`, время запроса, код `display_code`, текст «Подтверждайте только вход, который вы сами начали на сайте. Код должен совпадать с кодом в вашей вкладке». Код — помощь против ошибочного/обманного подтверждения; его наличие не делает пересланную ссылку безопасной.
4. Inline callback кнопки: «Да, войти» и «Отменить». Например `tga:ok:<challenge_id>` и `tga:no:<challenge_id>`; укладывать `callback_data` в 64 байта. Browser secret и JWT в callback запрещены.
5. Проверять `callback.from_user.id == challenge.telegram_id`, личный чат, TTL и ожидаемое состояние. Не доверять callback-data как доказательству личности. При одобрении проверить текущий allowlist.
6. Нажатие только меняет состояние. `/start` сам по себе никогда не авторизует.
7. Отвечать на callback, чтобы убрать индикатор ожидания Telegram. После сохранения `approved` отредактировать сообщение на текст успеха из раздела 1 и убрать кнопки. При повторном нажатии показать понятный итог. Если редактирование сообщения не удалось, не откатывать уже сохранённое подтверждение; корректно обработать ошибку доставки.
8. После «Отменить» пометить `denied`; браузер показывает отказ и предлагает новую попытку. На чужие, устаревшие и некорректные callback отвечать без исключений и без выдачи токена.
9. Обычный `/start` без параметров и старый `/start login` не могут авторизовать вкладку: дать обычную ссылку на сайт и инструкцию начать вход там. Не отправлять их автоматически в Mini App как «надёжный вход в браузере». Если Mini App сохраняется как самостоятельная функция, явно назвать его «Кабинет внутри Telegram».
10. Не нарушить `tariff_chat_member_handler` и другие функции этого же бота.

## 7. Изменения страницы входа

1. Оставить существующие обязательные чекбоксы; не менять их содержание в рамках этой задачи. Два ясных способа входа: текущий Telegram-виджет и всегда доступная после согласий кнопка «Войти через бота Telegram». Убрать два дублирующихся блока с одинаковыми советами про `/start`.
2. Создавать challenge по явному действию пользователя. Защитить от двойного клика; не создавать автоматически в React effect, который может выполниться дважды в StrictMode.
3. Сразу сохранить `{ challenge_id, browser_secret, bot_url, expires_at, display_code, return_to }` в `sessionStorage` вкладки. Обработать недоступное хранилище понятным сообщением; не отправлять пользователя в Telegram, если потеря связи с исходной попыткой уже неизбежна.
4. Открывать Telegram так, чтобы исходная вкладка оставалась доступной. Если используется `window.open`, открыть пустое окно синхронно внутри клика, затем назначить полученный `bot_url` и убрать `opener`. Блокировку popup обрабатывать явной обычной ссылкой «Открыть Telegram». На мобильных протестировать переход в приложение и возврат назад. Секрет browser не передавать новому окну.
5. Ожидание: «Подтвердите вход в Telegram. После этого вернитесь в эту вкладку». Показать код, оставшееся время, «Открыть Telegram ещё раз», «Проверить подтверждение», «Отменить». Не просить отправлять голый `/start`: он теряет идентификатор попытки.
6. Polling через последовательный timeout после завершения предыдущего запроса, каждые 3 сек. Только один активный status/complete запрос на попытку; отменять/игнорировать устаревшие ответы. В скрытой вкладке polling приостанавливать; на `visibilitychange`, `focus` и `pageshow` сразу проверить статус. Учитывать возврат из BFCache. Восстанавливать незавершённую попытку после reload из sessionStorage.
7. На `approved` выполнить `/complete`, сохранить JWT через `setStoredAuthToken`, затем выполнить общую логику успешного входа. На `consumed` после сетевого обрыва попытаться повторить `/complete` в допустимое окно. Не очищать сохранённый challenge до успешного получения и сохранения JWT.
8. При временной сетевой ошибке сохранять попытку и предлагать/делать ограниченный retry с backoff; 429 учитывать по `Retry-After`. Deadline брать с сервера, при возврате проверять серверное состояние: не терять уже consumed результат только из-за локального таймера.
9. При expiry/denied/cancelled показывать отдельную причину и кнопку новой попытки. Повторный переход в Telegram использует ту же живую попытку. Кнопка «Начать заново» отменяет старую перед созданием новой; старый ответ не может перезаписать новую попытку.
10. Уход со страницы очищает таймеры/listeners/AbortController, но не должен безусловно отменять запрос на сервере: это ломает reload и возврат. Отмена на сервере — по явной кнопке; забытые запросы истекают по TTL.
11. Если вход через виджет успел завершиться параллельно, остановить bot flow и отменить его challenge по возможности. Поздний callback/ответ не должен переключить сайт на другой аккаунт.
12. Сохранить путь возврата вместе с query/hash, а не только pathname. Разрешать только внутренние пути кабинета `/app` и `/app/…`; отклонять внешние адреса, `//`, backslash и циклические пути `/login`. Источник пути не должен позволять open redirect.
13. После сохранения JWT вызвать `/auth/me`: активная подписка → сохранённый путь или `/app`; неактивная → `/app/billing`. Временная ошибка `/me` не должна стирать корректный JWT или заставлять проходить Telegram заново. Недействительный JWT очистить и показать повторный вход. Убрать гонку преждевременного `<Navigate>` по одному лишь наличию только что сохранённого токена: завершение входа должно управляться единой функцией/состоянием.
14. Для нового exchange использовать отдельные auth-вызовы без глобального interceptor, который на 401 удаляет существующую пользовательскую сессию. Неправильный challenge не должен разлогинивать уже вошедшего пользователя.
15. `registration_complete` сейчас отправляется при каждом входе. Добавить отдельные события bot-login funnel без секретов; не расширять учёт регистрации неверными повторными событиями. Если различение регистрации/входа требует отдельного контракта, оставить это отдельным небольшим изменением.

Тексты ошибок: «Время подтверждения истекло. Начните вход заново»; «Вы отменили вход»; «Не удалось связаться с сайтом. Мы повторим проверку»; «Вход сейчас недоступен для этого аккаунта. Обратитесь в поддержку»; «Слишком много попыток. Повторите через …». Не объяснять пользователю работу backend, JWT или localhost.

Если сохраняется самостоятельный Mini App вход: заменить гонку загрузки SDK единой Promise с явным timeout/error и кнопкой повтора, не считать позднюю загрузку окончательным отсутствием initData; защитить effect от двойного запроса; не запускать этот сценарий одновременно с браузерным подтверждением. Блокировка загрузки виджета не должна блокировать новый способ вообще.

## 9. Проверки и критерии приёмки

Автотесты backend обязательны, поскольку это изменение авторизации:

- Без bot-confirm JWT получить нельзя; `/start` не подтверждает вход.
- Bot secret/публичного ID/знания Telegram ID недостаточно для status/complete без browser secret.
- Чужой callback, групповой чат, поддельный Telegram ID, истёкшая или отменённая попытка не авторизуют.
- Два браузера не получают сессии друг друга; запрос привязывается к одному Telegram ID.
- Двойное подтверждение и два одновременных complete возвращают один логический результат; повтор после потерянного ответа возвращает тот же токен в течение окна, после окна — отказ.
- Отмена/expiry во время complete корректно соревнуются с финальным условным UPDATE. Если complete уже committed, отмена не обещает отозвать сессию.
- Параллельное создание одного пользователя не вызывает 500/дубликаты. Проверять конкурентность на файловой временной SQLite с разными соединениями, не только in-memory StaticPool.
- Перезапуск процесса не теряет pending/approved запросы; очистка БД не требуется для соблюдения TTL.
- Allowlist работает при одобрении и получении JWT, включая изменение между этими шагами.
- Новый и существующий пользователь сохраняют правильного владельца проектов, подписку и attribution; отсутствующее фото в Bot API не стирает существующее.
- Недоступная/медленная проверка подписки не блокирует вход надолго и не выдаёт подписку ошибочно.
- Лимит status совместим с штатным polling; 429 корректен; секреты не появляются в логах/ошибках.
- Регрессионные проверки widget подписи из раздела 3 и Mini App, если он сохраняется.

Frontend: точечные тесты состояния polling/recovery/finish с fake timers и моками API, если тестовый инструмент уже появился к началу работ; иначе добавить минимальный подходящий инструмент, не строить отдельную большую тестовую платформу. Проверить StrictMode, двойной клик, reload, просрочку, закрытие, focus, отмену, stale response, сетевой retry и гонку widget/bot.

Команды существующего проекта: `python -m unittest discover -s tests -v`; во frontend — `npm ci`, `npm run build`. Миграцию проверить на копии БД или временной БД, не на production во время разработки. Проверить upgrade и сохранение существующих пользователей/данных. Тесты бота/Telegram API должны использовать моки и не отправлять реальные сообщения.

Ручной end-to-end прогон на тестовом окружении:

| Сценарий | Ожидание |
| --- | --- |
| Windows/macOS браузер + Telegram Desktop/телефон | Подтверждение в чате авторизует исходную вкладку. |
| iPhone Safari + Telegram; Android Chrome + Telegram | После возвращения в исходную вкладку вход заканчивается без дополнительных действий. |
| Новый пользователь бота | Понятно, что сначала требуется Start, затем подтверждение. |
| Пользователь уже общался с ботом | Новый start-параметр не теряется, показывается именно новая попытка. |
| Telegram Web, popup заблокирован, приложения Telegram нет | Есть работоспособная обычная ссылка и инструкция; исходная попытка сохраняется. |
| `telegram.org/js/*` заблокирован в браузере | Новый вход через бота работает без загрузки widget/WebApp SDK. |
| Возврат после 5 минут / cancel / сеть временно пропала | Отдельные понятные состояния и повтор без бесконечной загрузки. |
| Reload до/после подтверждения, потерян ответ complete | Попытка восстанавливается, идемпотентный повтор доставляет сессию. |
| Вход с фамилией и без неё через виджет | Оба работают, поддельная подпись по-прежнему отвергается. |
| Активная и отсутствующая подписка | Кабинет либо тарифы; отсутствие подписки не выглядит ошибкой входа. |

## 10. Настройки, выкладка и диагностика

Проверить фактическую конфигурацию без вывода секретов:

1. `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME`, `VITE_TELEGRAM_BOT_USERNAME` относятся к одному боту; сервер возвращает `bot_url`, frontend не собирает его из независимого имени для нового flow.
2. `PUBLIC_APP_URL` — канонический HTTPS origin сайта. API доступен с того же origin через `/api/`; это предпочтительный production вариант. Если API вынесен на другой origin, текущего CORS (только localhost) недостаточно — добавить точный production origin. Не открывать CORS всем без необходимости.
3. У существующего widget домен привязан через BotFather `/setdomain`. Для нового bot challenge эта настройка виджета не является механизмом подтверждения.
4. `JWT_SECRET_KEY` постоянен между перезапусками и не равен dev-default; `DATA_ENCRYPTION_KEY` корректен и одинаков у всех процессов, работающих с кешем результата. Не вращать ключи попутно без плана: это затрагивает текущие сессии/зашифрованные данные.
5. `ENFORCE_TELEGRAM_ALLOWLIST` соответствует принятому режиму доступа. Не включать/отключать ограничение молча как «исправление».
6. В `app/api/main.py` каждый startup запускает polling бота, scheduler и proxy manager. Для текущей архитектуры использовать один процесс приложения. При нескольких workers/репликах сначала вынести фоновые функции в отдельный процесс; общая таблица challenge сама по себе не решает конфликт polling.
7. Для одного токена бота не запускать конкурирующие polling-копии; проверить, что нет установленного webhook при использовании polling. Не вызывать `deleteWebhook(drop_pending_updates=True)` автоматически: можно потерять события, включая подписки. Тестовый и production боты должны быть разными.
8. Включить `callback_query` в реально получаемые updates, сохранив `message` и `chat_member`. При вычислении allowed_updates aiogram убедиться, что новые handlers зарегистрированы до start_polling.
9. Проверить синхронизацию серверного времени, reverse proxy headers, отсутствие кеширования auth-ответов, редиректы www/без www и клиентские timeouts. Не делать выводов о production по одному локальному `.env`.

Выкладка: резервная копия БД → миграция → backend с флагом нового входа off → проверка бота/API/ключей → frontend → включение → end-to-end проверка двумя тестовыми аккаунтами. Флаг должен управлять видимостью нового способа через серверную доступность/config; выключенный или некорректно настроенный backend даёт понятный `bot_unavailable`. Для отката выключить новый способ и вернуть UI; не удалять таблицу срочно и не ломать старый widget.

Метрики: start → bot_opened → approved → completed; отдельно expired/denied/failed и время этапов. Логи с безопасным correlation ID и кодом причины; без JWT, initData, browser/bot secret, полных URL Telegram и тела auth-запросов. Не логировать callback payload/сообщение `/start` целиком. Эти данные позволят отличить блокировку виджета, ошибку подписи, отсутствие нажатия Start, зависший polling и ошибку API.

## 11. Источники и ограничения решения

- [Telegram: deep linking](https://core.telegram.org/bots/features#deep-linking) — start-параметр и его ограничения.
- [Telegram Bot API: InlineKeyboardButton](https://core.telegram.org/bots/api#inlinekeyboardbutton) и [CallbackQuery](https://core.telegram.org/bots/api#callbackquery) — кнопки подтверждения и данные нажатия.
- [Документация используемого legacy Login Widget](https://core.telegram.org/widgets/login-legacy#checking-authorization) — проверка подписи; в возвращаемом объекте есть `last_name`.
- [Telegram Mini Apps: проверка initData](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app) — отдельный алгоритм существующего Mini App входа.
- [Актуальная страница Telegram Login](https://core.telegram.org/bots/telegram-login) — новый OIDC-flow существует; миграция на него не входит в данное задание.

Сценарий устраняет зависимость дополнительного входа от Telegram JavaScript в браузере, но пользователю всё равно нужен доступ к Telegram, а серверу — к Bot API. Существующее хранение access token в localStorage остаётся ради совместимости; переход всего приложения на HttpOnly-cookie/refresh tokens — отдельная задача. Закрытая вкладка с потерянным sessionStorage не может безопасно восстановить вход по одной публичной ссылке; нужно начать новую попытку.
