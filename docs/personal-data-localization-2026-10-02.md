# Персональные данные ThreadsGo: решение и план переноса

Дата проверки: 2 октября 2026 года. Это технический план и перечень вопросов для юридической проверки, а не заключение о полном соответствии законодательству.

## Решение для владельца

Смена threadsgo.ru на .com не устраняет требования к обработке персональных данных граждан России. Публикация ФИО не создаёт обязанность: оператором становится лицо, определяющее цели и порядок обработки. Если это владелец сервиса, в документах нужны его настоящие реквизиты; нельзя заменять их вымышленными данными или обозначением «администрация сайта».

Владелец подтвердил: сервер находится в Германии, уведомление Роскомнадзора не подавалось. Для обычной регистрации пользователей оснований рассчитывать на исключения из требований локализации не установлено. Дополнительное ограничение владельца: процессы работы с Threads должны остаться за рубежом. Рекомендация: сохранить домен, выделить российский контур учётных записей и основной базы, а процессы Threads оставить в Германии. Одного дополнительного российского зеркала при сохранении первичного сбора в Германии недостаточно.

## Разделённая архитектура с учётом ограничения владельца

Предпочтительный вариант: российский сервер принимает регистрацию/вход, сохраняет пользователей, согласия, подписки и проекты в российской базе; немецкий исполнитель получает только необходимые задания для работы с Threads. Публикации и доступ к Threads выполняются из Германии. К этой схеме нужно прийти постепенно: нынешний API одновременно обслуживает пользователей и запускает фоновые задачи, поэтому они ещё не являются независимыми сервисами.

Промежуточный технический вариант: весь нынешний API остаётся в Германии и подключается к PostgreSQL в РФ через защищённое соединение. Это переносит основное хранилище, но немецкий API всё равно получает данные регистрации и читает сведения из базы. Такой вариант нельзя объявлять окончательным решением 152-ФЗ без проверки маршрута первичного сбора, временных файлов/логов и трансграничной обработки. Удалённый доступ из Германии — не способ сделать иностранную обработку исчезнувшей.

Перенос одной таблицы `users` не покрывает всю информацию: Telegram ID есть в challenge входа, сведения о профиле и cookies — в `accounts`, идентификаторы владельцев — в проектах и промптах, исходные персональные сведения могут быть в контенте и событиях Tribute. Не заводить вторую `users` и синхронизацию между странами без новой модели доступа, согласованных связей и единственного источника данных.

Для небольшого российского узла ориентир конфигурации: 1–2 vCPU, 2 ГБ RAM, SSD и резервные копии, без браузеров Threads. Это стартовая оценка, а не подтверждённый предел нагрузки. Проверен Timeweb Cloud DBaaS: доступны регионы Москва и Санкт-Петербург, на публичной странице отдельно указаны IP 200 ₽ и backup 6 ₽/месяц за ГБ. Окончательная стоимость подходящей конфигурации не подтверждена: цена зависит от выбора ресурсов, региона и срока, цифру из заголовка страницы нельзя считать итоговым предложением. Самостоятельный VPS может стоить меньше, но потребует настройки PostgreSQL, обновлений и восстановления. Ничего не куплено.

Источник цены: [Timeweb Cloud DBaaS](https://timeweb.cloud/services/dbaas); [ограничения минимального PostgreSQL-тарифа](https://timeweb.cloud/docs/dbaas/dbaas-create). Не оплачивать неподтверждённую конфигурацию только ради минимальной цены.

## Какие сведения пока отсутствуют

- ФИО или наименование фактического оператора, адрес для обращений, рабочий email, правовой статус владельца.
- Выбранная российская площадка, подтверждённое физическое расположение базы и резервных копий.
- Перечень зарубежных получателей и фактический состав передаваемых данных. Нужна проверка Telegram, Tribute, DeepInfra и используемых прокси, а не только хостинга.

Не публиковать утверждение «сервис полностью соответствует 152-ФЗ», пока эти вопросы не закрыты. Не указывать российское размещение до фактического переноса. Cookie-баннер и согласия не легализуют иностранное размещение базы.

## Что именно переносить

В проекте используется SQLAlchemy; настройка `DATABASE_URL`, по умолчанию SQLite `data/app.db`. Перед переносом проверить действующее значение на сервере, не выводя его или секреты в общий отчёт. В базе находятся пользователи, подписки, проекты, задания, история операций и подтверждения Telegram-входа. Переносить согласованную копию всей базы, а не только таблицу пользователей.

Вместе с API и базой проверить `data/`, профили браузера (`CHROME_PROFILES_DIR`), расширения прокси (`PROXY_EXTENSIONS_DIR`), файлы cookies, журналирование, выгрузки и резервные копии. Сохранить `DATA_ENCRYPTION_KEY` и `JWT_SECRET_KEY` защищённым способом: смена ключа шифрования без миграции сделает сохранённые данные нечитаемыми. Не включать секреты в Git, инструкции или снимки экрана.

Удалённый файловый SQLite не использовать. Для внешней базы потребуется PostgreSQL: добавить и зафиксировать совместимый асинхронный драйвер, проверить схему и миграции на PostgreSQL, подготовить перенос типов JSON/enum/datetime, связей и последовательностей ID, затем проверить импорт на обезличенной копии. Простая смена `DATABASE_URL` существующие данные не переносит. Сейчас в зависимостях есть `aiosqlite`, драйвера PostgreSQL нет; подключение к российскому PostgreSQL пока не реализовано и не проверено.

## Порядок переключения без повторных публикаций

1. Подготовить российский сервер, HTTPS, закрытый доступ к базе и резервные копии в РФ. Сначала отделить пользовательский API от немецкого исполнителя и проверить контракт заданий. До копирования данных проверить площадку, доступы и возможность восстановления.
2. Проверить доступность Telegram, Tribute и поставщика генерации с новой площадки. Недоступность иностранного сервиса не обходить пересылкой всей базы или пользовательских cookies за границу; отдельно определить законную архитектуру передачи минимальных данных.
3. Снизить DNS TTL заранее. Зафиксировать план отката, окно обслуживания и незавершённые публикации. Откат в Германию нельзя считать решением локализации.
4. Остановить новые задания на старом сервере, дождаться завершения активных публикаций и операций. После остановки сделать согласованную резервную копию базы; для SQLite использовать backup API, а не копировать работающий файл без учёта WAL.
5. Защищённо перенести базу и необходимые файлы. Проверить целостность, количество пользователей/проектов/подписок, подарочные дни, очереди и возможность расшифровки. Не отправлять тестовые публикации от клиентов.
6. Запустить миграции на новой копии, затем API. Проверить вход существующего пользователя, регистрацию с согласиями, чтение проектов и сверку подписки. Не запускать два обработчика очереди или два polling-процесса Telegram одновременно.
7. Переключить DNS и входящие webhook, убедиться, что запросы идут на новую площадку. На старой оставить только техническую страницу обслуживания/перенаправление без приёма новых персональных данных на время обновления DNS.
8. Возобновить обработку очереди только на новом сервере. Для заданий с неопределённым результатом сначала проверить фактическую публикацию; не повторять автоматически.
9. Убедиться, что новые записи и резервные копии создаются в РФ. Закрыть старые процессы, токены доступа и копии данных в Германии по согласованному плану удаления и хранения. Учесть старые релизные backup-каталоги и логи; задокументировать фактическое удаление.

## Документы и уведомления

Подготовить уведомление Роскомнадзора от настоящего оператора с фактическими целями, категориями данных, местом базы и мерами защиты. Для трансграничной передачи отдельно проверить требования статьи 12, состав получателей и необходимость предварительного уведомления. Не подавать формы с вымышленной географией или датами. Для уже начавшейся обработки согласовать исправление ситуации с профильным юристом.

Довести политику и отдельное согласие до фактической схемы обработки: оператор, цели, данные, сроки хранения, обращения и удаление, поручения обработчикам, иностранные получатели. Маркетинговые рассылки и необязательная аналитика не должны включаться в согласие на регистрацию по умолчанию.

В подготовленных изменениях регистрации три отдельных подтверждения; сервер хранит дату, версию и назначение согласий. Повторный вход существующего пользователя не требует снова отмечать эти пункты. Историческим пользователям нельзя задним числом записывать согласия, которых они не давали. Подготовлен выбор аналитических cookies с отказом; Метрика запускается после согласия, Вебвизор выключен. Это технические меры, не замена локализации и документов.
