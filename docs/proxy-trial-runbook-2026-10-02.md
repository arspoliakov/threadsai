# Пробный тест двух sticky-прокси — 2 октября 2026

## Статус

Подготовлено исследование существующего жизненного цикла и изолированный `scripts/proxy_trial_probe.py`. Реальный запрос через нового поставщика **не выполнялся**, доступ не покупался, параметры работающих пользователей не переключались. Синтаксис sticky-сессий Proxly не установлен: скрипт не конструирует логины, session-id, географию или TTL. Нужны два полных URL, выданных поставщиком для двух разных тестовых sticky-сессий, и подтверждение разрешённого пробного доступа.

## Что тест проверяет

Два независимых клиента запускаются параллельно через барьер. Каждый последовательно делает три GET-запроса к единственному разрешённому небольшому HTTPS endpoint `https://api.ipify.org/`, с паузой 2 секунды. Используется тот же полный proxy URL внутри своей сессии; keep-alive отключён, поэтому повтор проверяет удержание выхода через новые TCP-соединения. Это важнее единичного запроса через один постоянный socket.

Нет Threads, Instagram, авторизации, публикаций, CAPTCHA, регистрации, платёжных операций или изменения production. Скрипт не импортирует `app`, `.env`, production settings или БД; `trust_env=False` исключает подхват системного HTTP_PROXY. Редиректы не разрешены, сертификаты HTTPS проверяются. Максимум 5 запросов на каждый из двух клиентов; жёсткий лимит времени до 60 секунд, timeout запроса 5 секунд. По умолчанию runtime 45 секунд. Обычный запуск без явного разрешения сети завершается отказом.

Счётчик `application_response_bytes` учитывает реально прочитанные тела HTTP-ответов, в том числе ошибки, с отключённым сжатием и пределом 512 байт на ответ. Он **не равен оплачиваемому трафику поставщика**: заголовки, запросы, CONNECT, TLS, повторные соединения и методика тарификации сюда не входят. Скрипт не может установить жёсткий лимит оплачиваемых байт у поставщика. Для live-теста нужен ограниченный trial без автопополнения/доступа к платному балансу; provider usage надо сверить отдельно до и после. Значение `provider_billed_bytes` намеренно остаётся `null`.

В отчёте нет proxy URL, логина, пароля или открытого IP. Адреса сравниваются через HMAC с новым случайным ключом для каждого запуска; идентификаторы пригодны только для сопоставления внутри этого отчёта. Ошибки транспорта выводятся по классу, без текста, способного содержать credentials. Скрипт не записывает файлы и отключает logging; самостоятельно не перенаправляйте секретные переменные в журналы.

## Проверка без сети

```powershell
.venv\Scripts\python.exe scripts/proxy_trial_probe.py --offline-check
```

MockTransport проверяет две независимые стабильные сессии, обнаружение ротации и совпадения выхода, а также отдельный счётчик response body bytes. Все ответы синтетические; `.env` и тестовые URL не читаются. Этот smoke прошёл 2 октября. Проверен также отказ обычного запуска без live-флагов; это не доказательство работы поставщика.

## Запуск после выдачи trial-доступа

Сначала получить у поставщика точные URLs и письменные ответы: sticky удержание между несколькими соединениями, максимальный TTL, поведение при недоступности exit-node, повторное использование одного session-id и shared exit между разными клиентами. Убедиться в ограниченной пробной квоте и отключённом платном автопополнении. Не использовать production credentials.

В PowerShell можно ввести URLs скрыто, без включения значений в историю команд:

```powershell
$env:PROXY_TRIAL_URL_A = [System.Net.NetworkCredential]::new('', (Read-Host 'Trial proxy URL A' -AsSecureString)).Password
$env:PROXY_TRIAL_URL_B = [System.Net.NetworkCredential]::new('', (Read-Host 'Trial proxy URL B' -AsSecureString)).Password
try {
    .venv\Scripts\python.exe scripts/proxy_trial_probe.py --live --trial-only --traffic-budget-bytes 4096 --samples 3 --interval 2 --max-runtime 45
} finally {
    Remove-Item Env:PROXY_TRIAL_URL_A, Env:PROXY_TRIAL_URL_B -ErrorAction SilentlyContinue
}
```

`--trial-only` — явное подтверждение оператора о пробных credentials; скрипт не способен проверить тип тарифного плана. `4096` ограничивает **только response body**. Увеличение этого значения не означает разрешения тратить платный баланс. Код 0 означает все запланированные запросы успешно прочитаны; код 2 — неполный тест/отказ. Дополнительно обязательно смотреть `ip_stable_in_observation`: полный тест с ротацией может вернуть 0, поскольку обнаруженная ротация является результатом измерения, а не техническим сбоем.

`same_exit_ip_observed=true` означает, что хотя бы один наблюдаемый выход совпал. `false` означает только отсутствие совпадения в короткой выборке, `null` — недостаточно данных. Это не гарантия отдельного IP. Стабильность в коротком тесте не гарантирует сохранение IP на протяжении 15 минут входа, 250 секунд публикации или после суток простоя. HTTP-тест не подтверждает совместимость Chrome auth extension или безопасность аккаунтов Meta.

## Что найдено в нынешней архитектуре

- `app/services/proxy_pool.py`: каждому Threads-аккаунту назначается уникальный порт из диапазона; общий host/login/password берутся из settings. Пользовательский proxy из импортированной сессии удаляется. Полный provider-issued URL и отдельный sticky session-id на аккаунт сейчас не хранятся. Поэтому смена одного общего host/login/password переключит сразу существующие аккаунты; для пилота так делать нельзя.
- `app/posting/proxy_manager.py`: сначала происходит claim реальной задачи, затем get_current_ip. В idle proxy-запросов уже нет — раз в 5 секунд проверяется очередь БД, а не IP. Discovery активных аккаунтов происходит раз в 30 секунд.
- IP читается **до** ожидания `browser_semaphore`. При очереди он может уже устареть к запуску Chrome. Для отдельного пилота надо брать browser slot прежде измерения expected IP и повторно проверять актуальность задачи/доступа после ожидания. Сейчас semaphore покрывает manager posting/scraping, но не session-check subprocess и не login-window.
- `app/posting/adapters/threads.py`: при выполнении задачи watchdog запрашивает ipify каждые 5 секунд, новым HTTP-клиентом. При смене IP закрывает браузер. Ошибка до попытки отправки может привести к повтору; после начала submission применяется защита неопределённого результата (`PublicationVerificationPending` / `publication_confirmation_pending`), профиль переводится на ручную проверку и автоматический повтор останавливается. Поэтому нельзя описывать ротацию как безусловный повтор отправки. Это полезно для текущего port-based удержания, но поставщик с ротацией на соединение немедленно столкнётся с этим механизмом. Проверить совместимость sticky между HTTP watchdog и Chrome на одном session-id нужно до подключения аккаунтов. Повтор без настоящей sticky не исправит эту несовместимость.
- `app/posting/profile_lock.py`: OS-backed lock на профиль аккаунта защищает Chrome profile между потоками и subprocess; профили разных аккаунтов отдельные и постоянные. Лимит Chrome browsers и защита одного профиля — разные механизмы. Нельзя убрать locks ради параллельности.
- `app/services/threads_login_window.py`: один глобальный pilot window, временный Chrome profile, TTL 15 минут, сохранение аккаунта на том же assigned port. Этот поток не использует общий browser semaphore и не запускает IP watchdog. Если residential TTL короче всего входа, ожидаемая стабильность не обеспечена. Проверка конца входа проверяет owner и cookies, а не подтверждает отдельный IP.
- На момент исследования discovery/claims и `require_active_subscription` проверяют только `subscription_status`; прямо на рубеже запуска не проверяют `subscription_expires_at`/`complimentary_access_expires_at`. Reconcile работает раз в 15 минут и опирается на Telegram membership; при отсутствии бота или недоступных чатах пропускает обновление. Следовательно, boolean может быть устаревшим, в частности после окончания подарочного доступа. Нельзя считать текущий boolean точным таймером окончания и использовать его как единственный ограничитель оплачиваемого traffic.
- В production не найден отдельный счётчик оплачиваемого proxy traffic. Ограничение cache Chrome и блокирование mp4/webm/audio URL не являются учётом трафика. JS, обычные изображения и fonts сохранены; объём реальной браузерной сессии может сильно отличаться от этого небольшого HTTP probe.

## Условия дальнейшего пилота

Не переносить существующие аккаунты на неподтверждённую shared-сеть. Следующий этап после удачного trial — изолированная provider abstraction с encrypted URL/session-id для специально разрешённого тестового аккаунта, согласованный TTL, лимит бюджета в кабинете поставщика и подтверждённый счётчик usage. Применять IP-проверку после ожидания slot, общий ресурсный лимит для check/login/tasks и актуальную проверку доступа. Наблюдаемая стабильность и разные IP не дают обещания отсутствия блокировок Meta.
