# Proxly: исследование перехода ThreadsGo

Проверено 2 октября 2026. Решение: кандидат для изолированного пилота, не одобрен для переноса действующих клиентов. Пакеты не куплены, настройки работающих пользователей не изменены. Условия ниже — опубликованные заявления поставщика, а не результаты проверки сети.

## Что сейчас в коде

- `app/services/proxy_pool.py`: общие host/login/password, аккаунту навсегда назначается отдельный `assigned_port`. Нет адаптера поставщика, lease sticky-сессии и счётчиков трафика.
- `app/posting/proxy_manager.py`: очередь выбирается по аккаунту, IP запрашивается после получения задания, но **до** `browser_semaphore`. Исправить порядок при внедрении нового исполнителя. Семафор локален процессу, поэтому не обеспечивает общий лимит между несколькими процессами.
- Браузерный профиль и файловая блокировка уже отдельные для каждого аккаунта (`app/posting/profile_lock.py`). Их сохраняем: смена поставщика не должна удалять cookies или создавать чужой профиль.
- Простаивающий основной worker не делает IP-запросы без задания. Отдельные восстановления прокси/проверки входа надо включить в общий бюджет и планировщик; «нулевой трафик в простое» нельзя обещать для всех фоновых путей без этой унификации.
- Watchdog в `app/posting/adapters/threads.py` проверяет IP отдельным HTTP-клиентом каждые 5 секунд. При отсутствии настоящей sticky-привязки это может проверять другой выход, а каждый запрос расходует трафик. Таймаут проверки не доказывает неизменность IP.
- Фильтрация использует `subscription_status`; при допуске задания нужна непосредственная проверка актуального срока доступа, включая подарочные дни, а не только флага после фоновой сверки.
- Механизм неопределённого результата публикации уже есть. Сохраняем остановку/ручную сверку, не включаем автоматическую повторную отправку.

## Архитектура внедрения

1. Добавить `ProxyProvider` с двумя реализациями: `legacy_port` и `residential_sticky`. Старые аккаунты остаются на `legacy_port`. Новые поля/таблицы добавляются без удаления `assigned_port`; флаг пилота задаётся отдельно на аккаунт.
2. Очередь хранит `waiting`, краткосрочную бронь и `running`; ожидание браузера не должно выглядеть как работа Chrome. Один активный lease на аккаунт обеспечивается транзакцией в БД с fencing token и временем истечения. Существующая файловая блокировка профиля остаётся вторым барьером. Все публикации, сбор данных, проверки входа и окно подключения проходят один контроллер мощности; отдельные входы не обходят лимит.
3. Последовательность: получить свободный слот браузера → блокировку аккаунта/профиля → повторно проверить оплаченный/подарочный доступ и бюджеты → выделить sticky lease → проверить внешний IP этим же подключением → запустить Chrome с теми же реквизитами → непосредственно перед отправкой ещё раз проверить доступ и действительность lease. Освобождение в `finally`; после задания Chrome и соединения закрываются. Профиль на диске не расходует трафик.
4. Session-id — случайный непрозрачный идентификатор без email/имени. Разные аккаунты имеют разные идентификаторы. Точный формат и возможность повторного использования определяет поставщик. Проверенные IP сравниваются перед параллельным допуском: при совпадении можно отложить второй аккаунт, но нельзя обещать эксклюзивность или бесконечно вращать IP в поиске «чистого» адреса.
5. У аккаунта хранить provider binding; у запуска — lease-id, время, страна, защищённый отпечаток IP, причина остановки и расход. Секреты шифруются/хранятся в закрытой конфигурации, не возвращаются клиентскому интерфейсу и не пишутся в лог. Cookies и профили изолируются по владельцу и аккаунту.
6. По окончании доступа новые задания не запускаются. Если доступ закончился до нажатия «Опубликовать», отправка отменяется. После нажатия разрешена только сверка результата, без новых публикаций. Остаток пакета принадлежит общему балансу сервиса, не «сгорает» вместе с подпиской конкретного клиента.
7. Для нескольких процессов заменить локальный семафор общими lease слотов в БД/очереди; для одного процесса допустим общий семафор при условии, что все пути действительно используют его. Брошенные lease снимаются по таймауту, но это не разрешает повторную публикацию с неизвестным результатом.

## Сбои и отсутствие дублей

| Событие | Действие |
| --- | --- |
| Обрыв до отправки | Закрыть браузер; ограниченный повтор с задержкой и повторным допуском по сроку/бюджету. Не менять IP внутри открытого профиля молча. |
| IP сменился или проверка недоступна | До отправки остановить задачу; при смене выхода закрыть Chrome. Не продолжать публикацию с непроверенным lease. |
| Сессия входа истекла | Статус «нужно переподключить», понятное уведомление владельцу; никаких бесконечных попыток входа. |
| Ограничение Threads | Остановить аккаунт и предложить владельцу проверить его. Не обходить проверку и не увеличивать активность. |
| Отправка могла произойти | До клика записать `submission_started` и attempt-id. При потере ответа перейти в `publication_unknown`, запретить повтор. Сверить собственные посты и сохранить внешний id; если доказательства нет — ручная проверка. |
| Цепочка частично опубликована | Хранить id каждой подтверждённой части и связь reply. Не повторять всю цепочку. Неизвестная часть блокирует её продолжение. |

Локальный attempt-id не является идемпотентным ключом Threads. Совпадение текста само по себе недостаточно для безопасного автоматического признания результата. После падения процесса запись `submission_started` также требует сверки.

## Учёт и цена

Источником оплачиваемого расхода является счётчик поставщика/дельта баланса, а не размер страницы. Нужны API статистики, точность и задержка обновления. Для распределения между пользователями — серверный транспортный счётчик входящих/исходящих байтов по job/lease, например локальный relay перед внешним прокси. CDP `encodedDataLength` — дополнительная оценка загрузок браузера, не полноценный биллинг: не включает весь исходящий трафик и накладные расходы. IP-проверки, неудачные попытки, соединения и watchdog тоже учитываются.

Ledger: пользователь, аккаунт, задача, lease, транспортные байты в обе стороны, оценка браузера, подтверждённые байты поставщика, цена партии трафика и степень точности. Общую необъяснённую разницу учитывать отдельно, не выдавать её за точный расход клиента. При параллельных задачах общая дельта провайдера сама по себе не даёт точного разделения. Перед запуском резервируется бюджет с запасом; локальные лимиты и аварийный выключатель защищают от перерасхода, но запаздывающая статистика провайдера не гарантирует точное отключение на последнем байте.

**Измеренного трафика пока нет: тестовые реквизиты не предоставлены.** Ниже только расчёт сценариев, предполагающий десятичный ГБ = 1000 МБ; поставщик должен подтвердить единицы и состав списания.

| Оплачиваемый объём | Proxly, пакет 1 ГБ | Proxly, пакет 10 ГБ | Proxymarket, оценка пользователя |
| --- | ---: | ---: | ---: |
| 10 МБ | 1,20 ₽ | 1,12 ₽ | 4 ₽ |
| 100 МБ | 12 ₽ | 11,20 ₽ | 40 ₽ |
| 1 ГБ | 120 ₽ | 112 ₽ | 400 ₽ |

Тарифная экономия составляет 70–72% при одинаковом оплачиваемом объёме. Это не измеренная экономия на аккаунт: новый маршрут может расходовать больше из-за обрывов/повторных загрузок. Сервер, ИИ, хранение, платежи и сопровождение в таблицу не включены. Пакет 10 ГБ требует сразу 1120 ₽; не покупать до пилота. Себестоимость запуска = подтверждённый расход / единица ГБ × цена израсходованной партии. Месяц = сумма фактических запусков + относимые фоновые расходы.

## Пилот и критерии перехода

Первый этап — самостоятельный `scripts/proxy_trial_probe.py`, две явно заданные URL с разными подтверждёнными session-id, без импорта настроек production, доступа к БД и входа в Threads. Порядок и ограничения описаны в `docs/proxy-trial-runbook-2026-10-02.md`. Реальную сеть запускать только после получения тестового доступа. Маленькие HTTP-запросы проверяют транспорт и наблюдаемую стабильность, но не доказывают работу двух браузеров или длительное сохранение входа.

Затем отдельный изолированный браузерный тест без аккаунтов: два временных профиля, тот же шлюз для IP-проверки и Chrome, ограниченные публичные страницы/время/трафик, проверка выхода после захвата слотов. Только после успешного этапа и подтверждения условий — один разрешённый владельцем тестовый аккаунт с новым отдельным профилем, несколько перезапусков после idle и после TTL. Сохранение cookies не гарантирует сохранения того же IP или доверия Threads.

Переход допустим после письменных условий, измерения оплачиваемого трафика, проверки двух сессий и одного аккаунта между запусками; затем небольшой добровольный пилот. Тест отсутствия дублей проводить на локальном имитаторе ошибок, не публикуя лишние посты в реальный аккаунт. Действующих пользователей мигрировать только отдельным решением. Откат меняет маршрут между заданиями, не удаляет профиль и не повторяет неизвестную публикацию.

## Что запросить у Proxly

Подготовленные вопросы, **не отправлены**:

1. Дайте точный пример sticky HTTP и SOCKS5, правила session-id, API создания/закрытия/продления, максимальный TTL и idle timeout. Какая страна доступна для теста?
2. Каковы отдельные лимиты sticky-сессий, TCP-соединений, соединений на session-id, скорости и запросов? Есть ли доплаты?
3. Что произойдёт при отключении резидентного узла: ошибка или автоматическая смена IP? Есть ли режим отказа без подмены выхода? Сохраняется ли IP после закрытия браузера/перезапуска и повторного session-id?
4. Может ли один IP достаться двум нашим session-id или чужим клиентам? Есть ли гарантия разных IP и эксклюзивный тариф?
5. Разрешено ли одному серверу ThreadsGo использовать общий оплаченный баланс для автоматизации собственных аккаунтов клиентов, не передавая им пароль шлюза? Есть ли специальные требования/запреты на авторизованную работу Threads?
6. Как считаются ГБ: 10^9 или 2^30 байт; входящий/исходящий поток, CONNECT/TLS, DNS, ошибки, округление? Дайте API баланса и статистику по session-id с задержкой/точностью. Что происходит с остатком при неактивности, прекращении услуги и изменении цены?

Для теста нужны подтверждённые реквизиты trial Residential (host/port, секреты и реальный формат sticky), доступный остаток, страна, TTL/лимиты и снимки счётчика до/после. Передавать секреты через закрытую конфигурацию тестового окружения; отчёт их не содержит. Покупка и перенос клиентов не входят в это исследование.
